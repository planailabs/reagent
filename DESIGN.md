# reagent

A resumable coding agent for long-running work on the projects on one machine, built on [subagent-net](../subagent-net) (subnet). You register project folders, start tasks in them (by hand, from cron, from other tasks, or from agents outside over MCP), and watch and steer them in a web interface. Tasks run shell commands (foreground, background, interactive terminals), edit files, work in git worktrees and merge back, and keep notes in a markdown memory per project and a global one.

This document describes reagent as built; the Status section at the end lists what's implemented and what isn't.

## Decisions

| | |
|---|---|
| Shape | One Rust workspace pinning subnet by git rev; `reagent up` runs the hub, a node, reagent's MCP servers and the web server in one process (like Vesper). A separate `reagent supervisor` process owns commands and terminals. |
| Models | Any OpenAI-compatible endpoint (base URL, key from env, model name), as profiles. |
| Users | One user, reachable remotely: password login and a cookie session; TLS from a reverse proxy in front. Agents outside sign in to the MCP API with API tokens. |
| Command safety | Unsandboxed, as the user. A policy per project: allow / ask / deny by tool, command pattern and target; ask parks the call until it's approved. |
| Tasks | One subnet agent per task, in one project. Subtasks are tasks of their own (root agents) that reagent links to their parent: their reports come to it as messages. |
| Worktrees | The agent decides: tools to start a worktree, see its diff, merge it back, drop it. Merging is auto or needs approval, per project. |
| Commands | Foreground (the task waits), background jobs, and PTY terminals. A foreground command moves to the background at its timeout or from the UI ("move shell to background" on the task's page, for one that looks stuck). |
| Memory | Markdown: an `INDEX.md` per scope (global, each project) linking topic, folder and task files. Stored centrally, or in the project's repo, per project. The indexes are injected; tools read and change the files. |
| Skills | The generic layout: `.agents/skills/<name>/SKILL.md` (and `.agent/skills/`, `.claude/skills/`) in the working directory, the project and globally (`~/.agents/skills/`, `<data>/skills/`). Names and descriptions are injected; a tool loads one. `AGENTS.md` is injected too (the global ones, `~/.agents/AGENTS.md` and `<data>/AGENTS.md`; the project's; a subfolder's once the task touched a path under it), and its rules (`.agents/rules/`: always, by the files touched, or listed by description). |
| Cron | Per project, in reagent's database, managed in the UI (and by tasks through tools). |
| Storage | SQLite for everything: reagent's own data, and subnet's hub through subnet's SQLite backend. |
| Notifications | Web Push and the apprise CLI. |
| Platforms | Linux and macOS (Unix PTYs, process groups, Unix sockets). |

## Processes

```
reagent supervisor   (long-lived; outlives restarts of `reagent up`)
  owns: jobs (sh -c, each in its own process group) and PTYs; logs and scrollback on disk
  talks: Unix socket <data>/supervisor.sock (newline-delimited JSON)

reagent up
  subnet hub (SQLite <data>/hub.db) + one node ("local")
  reagent's MCP servers for tasks: fs, shell, pty, git, memory, skills, tasks, ask, and the hooks
    (HTTP on a loopback port, /mcp/<server>, a token only the node has)
  followers: reports, task states, approvals, usage and budgets, job ends, compaction checkpoints
  cron scheduler, triggers, services (each a supervisor job, looked after every second), notifier
  web server (axum, reagent.hcl's listen): the UI, /api (JSON, SSE, WebSocket), /mcp (the MCP API)
```

`reagent up` starts the supervisor if none answers on the socket (`reagent supervisor`, detached in its own process group). Restarting `reagent up` (an upgrade, a crash) leaves every command running: on start it reconnects, and job ends it missed are passed on. Stopping (`Ctrl-C`) quick-pauses all running tasks first (running tool calls finish, nothing new starts), records them (`paused-at-stop.json`), and resumes them at the next start. Task agents of an older version (reagent.hcl or reagent changed) are upgraded: at start, and by the follower until it works (an upgrade fails while the node is still connecting its servers). reagent's own MCP servers keep their port across restarts (`mcp-port`): their URLs are part of their identity in subnet, so a new port would make every running task outdated. `reagent supervisor --stop` ends the supervisor and everything it runs.

The supervisor's protocol: a request is `{"rid": n, "op": …}`, its answer `{"rid": n, "ok": …}` or `{"rid": n, "err": …}`; a connection that subscribed also gets `{"event": …}` lines (a job's output, a terminal's bytes with its scrollback first, every job's end). Ops: `spawn`, `jobs`, `job`, `wait` (until it ends, is moved to the background, or a timeout), `background`, `input`, `kill` (the whole process group), `ack` (its end was passed on), `pty_open`, `pty_send`, `pty_screen` (rendered by the `vt100` crate, after it's been quiet for a while, with scrollback), `pty_resize`, `pty_close`, `ptys`, `subscribe`, `shutdown`. A job running when the supervisor died is marked `lost` at its next start.

Data lives under the platform data dir (`directories`: `~/.local/share/reagent`, `~/Library/Application Support/reagent`), or `--data`, or `REAGENT_DATA`:

```
reagent.hcl          providers, model profiles, notifications, listen address (an example is written the first time)
.env                 secrets (read at start)
reagent.db           projects, rules, tasks, cron, settings, sessions, push subscriptions, notifications, API tokens
hub.db               subnet's store
cluster.hcl          the cluster file reagent made (for reference)
supervisor.sock, supervisor.log
jobs/<id>/           meta.json, output.log (stdout and stderr, as they came)
ptys/<id>/           output.log (the terminal's bytes)
memory/INDEX.md      the global memory
memory/projects/<project>/   a project's memory (when kept centrally)
worktrees/<project>/<branch>/  worktrees (when kept centrally)
paused-at-stop.json  tasks the last stop paused
```

## What subnet got for reagent

- **A SQLite store** next to Postgres, chosen by the database URL; migrations for both, kept equal (tested); leader election by a lock file next to the database. The whole subnet suite runs on either (`SUBNET_TEST_DB=sqlite`).
- **Who calls an MCP tool:** every tool call carries `_meta` with `subnet/agent` (and `subnet/parent`, `subnet/tenant`), also when routed through the hub: one reagent server serves every task and knows which one calls.
- **A pause during `pre_model` hooks holds the model call** until a resume (which makes it without asking the hooks again): the budget check in the context hook stops a task before its next call.

Besides: hooks (pre_tool with ask, pre_model with inject, pre_compact), approvals, pause modes, compaction, upgrades, `grep_results` and `search_history` were there.

## Projects

A project is registered in the UI (or the API): an id (lowercase, `-`), a name, a folder (one project per folder), and settings:

| setting | |
|---|---|
| `memory` | `central` (default: `<data>/memory/projects/<id>/`) or `repo` (`<folder>/.reagent/memory/`, committable) |
| `worktrees` | `central` (default: `<data>/worktrees/<id>/`) or `repo` (`<folder>/.worktrees/`, kept out of git status through `.git/info/exclude`) |
| `merge` | `approve` (default) or `auto` |
| `default_action` | what a call no rule covers gets: `ask` (default), `allow` or `deny` |
| `profile` | the default model profile for its tasks |
| `budget` | per task (`tokens`, `cost`, `minutes`) and for the project per day (`daily_cost`: no new tasks past it) |
| `env` | extra environment for its commands |
| `worktree_sharing` | `shared` (default) or `exclusive`: whether tasks share a persistent worktree or take it one at a time (each worktree may set its own) |
| `devshell` | `auto` (default: when the working directory or the folder has a `flake.nix`), `on` or `off`: commands and terminals run in its nix dev shell (`nix develop <flake>[#devshell_attr] --command sh -c …`, per command: exact, nothing cached to go stale); `devshell_attr` picks another shell (`ci`); a command opts out with `devshell: false` |

A new project gets the starter rules (below).

### Persistent worktrees

A project may keep named, long-lived git worktrees: a branch checked out apart (a feature in progress, a release line) that tasks start in instead of the project folder. Each is a row in `persistent_worktrees` (project, name, path, branch, base, sharing, adopted, created):

- **Made** by reagent (`name`, `branch` (default: the name; an existing branch is checked out, else a new one is made from `base`), `base` (default: the branch the project folder is on)) in `<worktrees>/<project>/persistent/<name>` (central or in the repo, as the project's `worktrees` says), or **adopted**: a worktree git already knows (`git worktree list`: not the project folder, not a task's own) is recorded as it is; the listing offers them.
- **Picked** when a task starts (the UI's new-task tab and quick prompt, the APIs, the CLI, templates, `task_spawn`): the task's working directory is the worktree, which is its `home`. It edits and commits there directly, as it would in the project folder. A subtask in the same project starts in its parent's home unless it's given another (or `worktree: ""`, the project folder).
- **Merges come home.** A task with a home that starts its own worktree (`git.worktree_start`) branches from the home's branch, and `git.worktree_merge` merges back into it (into the home's checkout); another base is refused. `worktree_drop` brings the task back to its home. Its files (`fs.*`, the shell) may reach the home too.
- **Sharing.** `shared`: any number of tasks work there at once (the project's and the global limits still count). `exclusive`: one top-level task at a time (with its subtasks); another queues until it ends. The worktree's `sharing` (none: the project's `worktree_sharing`) decides.
- **The person** sees each one's branch, base, commits ahead, uncommitted changes, the diff against the base and the tasks that worked there; merges it into its base (`merge`, `squash` or `rebase`, as for a task's worktree; conflicts are aborted and named); and removes it: refused while an active task is in it, and while it has work not in its base (unmerged commits, uncommitted or untracked files) unless forced (the work is discarded); an adopted one is only forgotten unless the removal says `delete`. A removed worktree's tasks keep their record (`home`).

## Tasks

A task is a subnet agent spawned (as root) from the mixture `task-<profile>`, with reagent's record in `reagent.db`: project, parent, title, prompt, origin (`ui`, `cron:<id>`, `task:<parent>`, `mcp`), working directory (the project folder, its persistent worktree (`home`), or its own worktree), profile, budget, skills loaded at start, state, what it waits for, report (the last; every report it made is kept, in `reports`, since a task that's over goes on with a message and reports again), tokens and cost, and the agent's id. States: `queued` (waiting for a place: see below), `running`, `waiting` (for an approval, an answer, a merge, or over budget), `paused`, `done`, `failed`, `cancelled`.

**Tasks at once.** The person limits how many tasks run at once: for all of reagent (`max_tasks` in the settings: the web UI's settings page, `PUT /api/settings`) and per project (its `max_tasks`, on its settings tab); none: no limit. A task in an `exclusive` persistent worktree also waits while another top-level task works there (running, waiting or paused: its changes are there). A task takes a place while it's `running` or `waiting` (a paused one gives its place up; a person's resume doesn't wait for one). A task started over a limit is recorded as `queued`, without an agent; queued tasks start oldest first as places free (checked every 1.5 s, so a raised limit or a project's own takes effect at once). Subtasks don't count and never wait (their parent waits for them: no deadlock). A **repair task** (origin `trigger-repair:` or `service-repair:`) starts only when nothing else goes on in its project: no other task there running or waiting, none queued but repairs; otherwise it's queued behind them and starts once the project is otherwise idle (paused tasks don't hold it back; two repairs go one after the other; "start now" starts it anyway). A message for a queued task is added to its prompt; it can be cancelled, or started at once by the person ("start now", `POST /api/tasks/{id}/start`). Its time budget counts from when it started (`started`). Cron entries, triggers and the APIs start tasks the same way, so they queue too.

- **Starting:** from the UI, the API, the MCP API, cron, or a task (`tasks.task_spawn`). The first message says the task, the project, the working directory and the task's **scratchpad** (`<temp>/reagent-scratch/<task id>`, the OS's temp folder: its own for each task, subtasks too, mode 0700, made again when it's gone; reagent never removes it, the OS's temp cleanup does; the system prompt says temporary scripts and outputs go there, not into the project), then the prompt, then the bodies of the skills asked for. The title may be left out (the UI, the APIs, `task_spawn`): the task is shown as "untitled task" and its first message asks it to name itself first with `tasks.task_title(title)` (a few words, 1 to 120 characters; the UI hears it live; a task may rename itself later too; allowed by the starter rules and, for existing projects, a migration). Its budget: each limit asked for, else the project's; `unlimited: ["tokens"|"cost"|"minutes"]` (`POST /api/tasks`) leaves those off, the project's too. A project over its daily cost starts nothing.
- **Steering:** a message (read before its next model call; a finished task goes on with it), pause (quick: running calls finish; safe: after this turn), resume, cancel (its jobs and terminals end too), approve or deny a call (or "always": a rule allowing the tool with that command goes in front), answer a question, merge or send back a worktree, retry a failed task (subnet resumes it where it failed: the model call again), raise its budget (a task paused over it goes on), change its profile or budget (a new profile applies when it next starts: subnet keeps an agent's type).
- **Following:** reports come to root's mailbox (a task is done, failed or cancelled); a loop every 1.5 s reads the agents' phases, the call waiting for approval, usage (cost from the profile's prices: cached prompt tokens at `price.cached`; a task's earlier agents, before an upgrade or a model switch, stay counted: carried over at the move, and counted again from the superseded agents at every start) and budgets. Job ends become messages to their task (which wakes it), except for a foreground command a tool still waits for. A subtask's report becomes a message to its parent.
- **Messages** (the person's, an outside agent's, another task's, a subtask's report, a job's end, an answer with no question waiting) are **queued**: kept in reagent.db (`outbox`) and the call returns at once; a worker per task hands them to the agent in order (`Send` on the hub, which waits until the agent takes it), claiming each before it sends it (`sending`; claims are undone at a start, so one cut off is sent again) and removing it once taken, retrying with backoff (1 s up to a minute) while it fails, dropping them when the task is cancelled or gone. A paused task's messages wait in the queue until it's resumed (any resume: the follower looks again every 15 s). Until claimed, the person's own queued messages (typed on the task's page; `person` in `outbox`) can be changed (`PUT /api/tasks/{id}/queued/{mid}` `{text}`) or cancelled (`DELETE /api/tasks/{id}/queued/{mid}`; all of theirs at once: `DELETE /api/tasks/{id}/queued`); the others (a job's end, a report, an answer, an agent's or another task's message) are shown, marked as reagent's, and can't be. A done or failed task is set running when its message is taken. Messages still queued at a stop are delivered after the next start. A sleeping task is woken when its message is queued. The task's queued ones show on its page and in the API's task (`queued_messages`). A message to a cancelled task is refused.
- **Long runs:** compaction at three quarters of the profile's context; the `checkpoint` hook (pre_compact) asks for a summary someone could pick the work up from, and reagent writes each summary into the project's memory (`tasks/<id>.md`, linked from the index). The budget is checked before every model call (the `context` hook pauses a task over it, which holds the call) and by the follower.
- **Long calls:** reagent's MCP sessions have no idle timeout (rmcp's default of 5 minutes ended a session with a question still open in it, and the node waited for an answer that couldn't come); the MCP API's sessions end after 6 idle hours.
- **Waiting across a restart:** a question or a merge waits in its tool call, and is stored with the task (its `wait`). `ask` and `worktree_merge` are idempotent: after a restart subnet runs the call again, which finds the stored wait (and isn't announced again). An answer or a merge decision given while nothing waits (reagent was restarting) is kept in the wait and taken by the call when it runs again; if the call is gone for good, it goes to the task as a message. A stop doesn't wait for tasks waiting for the person. An approval survives too (it's subnet's).

**Kinds and models.** reagent.hcl names kinds of task: `kind "research" { profile = "big", escalate = "bigger", escalate_after = 5 }`; a kind may also have a `prompt` (its role: a "# Your role (<kind>)" section before the task's prompt in its first message) and `tools` (globs over `<server>.<tool>` its tasks may use, `added.*` for every added MCP server's; none: all; the policy hook refuses the rest, saying what the kind is for). reagent has four of its own, for helpers a task delegates to with `tasks.task_spawn(kind=…)`: `explore` (find and read code, configs and history, answer with file:line; reading tools and `shell.exec`; no file edits), `review` (check a change or a claim, run tests, report findings worst first, fix nothing; reading tools and the shell), `code` (make a change completely with its tests; every tool), `research` (look things up with the added MCP servers, e.g. firecrawl, cite sources; reading tools and the added servers' tools). A kind reagent.hcl defines with one of these names is its own instead, whole. Delegation is always a subtask: subnet's `spawn_agent` (which subnet offers every agent) is refused by the policy hook with a pointer to `task_spawn` and the kinds. A subtask's report reaches its parent unless the parent was cancelled: a parent that ended its turn ("waiting for it") is woken by it. A task's kind is the one it's started with (UI, API, `task_spawn`, cron, the MCP API), else by origin (`routing { subtask, cron, mcp }`), else the project's `kind`, else `default_kind`; its profile is the one asked for, else its kind's, else the project's, else `default_profile`. A task moves onto another profile with its whole history (subnet's `upgrade … to` another mixture): the person does it (the task page, `POST /api/tasks/{id}/profile`, the MCP API's `task_switch_profile`); the task does (`tasks.task_escalate(why, profile?)`, to its kind's `escalate`, after its current call); and it happens by itself after `escalate_after` tool errors in a row. A profile's `fallback` takes a task whose model call failed there (once per profile, no back and forth): it's retried on the fallback. Each move is a `model` notification.

**The agent type.** reagent writes the cluster from `reagent.hcl` at every start: node `local`; per profile an agent `model-<profile>` (its provider's URL and key env, model, params, the system prompt `prompts/task.md`, `search_history`, `grep_results`, hooks `policy`, `mask`, `context`, `checkpoint`, compaction) and a mixture `task-<profile>` with reagent's servers; the servers (`url`, a bearer token from `REAGENT_MCP_TOKEN`, their idempotent tools); the hooks. `spawns = []`: tasks start subtasks through reagent, not subnet's `spawn_agent`.

## Tools

The MCP servers of `reagent up`, for tasks only. Each call says which agent calls (`_meta.subnet/agent`), so paths, jobs and terminals are that task's. A path is relative to the task's working directory and must be inside its places (the working directory, the project folder, the memories, its scratchpad; skills' folders for reading), unless a rule with a matching `target` allows it.

Besides these, subnet gives every task `search_history` (its own whole conversation) and `grep_result` (a long tool result, which reached it cut, searched or read by lines).

**Files (`fs`)**
| tool | |
|---|---|
| `read(path, from?, to?)` | lines, numbered, 400 at a time; the end says where to read on |
| `write(path, text)` | makes (with its folders) or replaces a file |
| `edit(path, …)` | `old`/`new` (exactly once, or `all`), or `op: append / insert (line or after a passage) / delete (lines or a passage)` |
| `grep(pattern, path?, glob?, context?, page?)` | regex over files, respecting `.gitignore`; case-insensitive unless the pattern has capitals; 100 a page |
| `glob(pattern, path?)` / `ls(path?)` | files by pattern (500 at most) / a folder |

**Commands (`shell`)**
| tool | |
|---|---|
| `exec(cmd, cwd?, timeout?, stdin?, devshell?)` | `sh -c` in the foreground: exit code and output (the last 60 000 characters). Past `timeout` (default 600 s), or when the person moves it (the task's page lists the foreground commands it waits for, with how long each has run and its last lines, and a "move shell to background" button), it goes on as a background job: the call says so (and that the person moved it, so it may be stuck: hanging or waiting for input), with the output so far and the tools to follow, answer or stop it. |
| `exec_bg(cmd, cwd?, name?)` | a background job, its id at once; its end comes as a message |
| `jobs()` / `job_output(job, from?, to?, tail?, pattern?)` / `job_wait(job, timeout?)` / `job_input(job, text, close?)` / `job_kill(job, signal?)` | list, read, wait, write to stdin, signal the process group |
| `sleep(duration? \| until?)` | waits (`90s`, `10m`, `2h`; or until `HH:MM`, the next one in the machine's time zone, or an RFC 3339 time; at most 7 days) to look at something outside again; a message to the task (the person's, a subtask's, a job's end, a trigger's) wakes it early. Allowed in every project (a starter rule; migration 0016 adds it). Run again after a restart: a duration starts over |

Commands get the project's env, `REAGENT_TASK`, `REAGENT_PROJECT`, the task's scratchpad as `REAGENT_SCRATCHPAD` and as `TMPDIR`, `TMP`, `TEMP` (in a dev shell nix develop makes its own temp folder inside it), and `PAGER=cat`, `GIT_PAGER=cat`, `GIT_EDITOR=true` (nothing waits for a person).

**Terminals (`pty`)**: `pty_open(cmd?, cwd?, cols?, rows?)`, `pty_send(pty, keys, quiet_ms?)` (text with `<enter>`, `<tab>`, `<esc>`, arrows, `<bs>`, `<C-x>`…; answers with the screen once it's quiet), `pty_screen(pty, quiet_ms?, scrollback?)`, `pty_close(pty)`, `ptys()`. The person sees and types into the same terminals (xterm.js).

**Git (`git`)**: `worktree_start(branch?, base?)` (branch `reagent/<title>-<id>`, from the project's current branch, or the branch of the task's persistent worktree (the only base it may have); the working directory moves there), `worktree_status()`, `worktree_diff(stat?)`, `worktree_merge(strategy?, message?)` (`merge`, `squash` or `rebase`; the worktree must be clean; with `merge = "approve"` it waits for the person, who sees the diff and merges or sends it back with a message; conflicts are aborted and named, to resolve in the worktree), A task that ends its turn with uncommitted files or unmerged commits in its own worktree isn't done yet: reagent sends it a message (naming what's left) to commit what belongs to the change and request the merge with `worktree_merge`, or to say why not and drop it; once per state of the worktree, so ending again without a change is taken as its answer (then it's done as usual). `worktree_drop(discard?)` (refused while it has work not in its base: unmerged commits, uncommitted or untracked files; `discard` throws that away, and always waits for the person's approval, whatever the rules say). No worktree's work is deleted unless it was discarded explicitly: a task's by the person's approval, a persistent one's by `force` (the UI's remove names what goes and asks first). Into a checkout of the base (the one there is, else a temporary one); a commit reagent makes there (a merge, a squash, a rebase) is `reagent <reagent@localhost>`'s where git has no `user.email` (logged); the git CLI does it (merges and worktrees aren't in gitoxide).

**Memory (`memory`)**: see Memory. **Skills (`skills`)**: `skill_list()`, `skill_load(name)`.

**Tasks (`tasks`)**: `task_title(title)` (names the task), `template_list(project?)` (prompt templates), `task_spawn(title?, prompt?, template?, values?, project?, profile?, kind?, skills?, budget?)`, `prompt_design(goal, project?)` (see The designer), `task_escalate(why, profile?)`, `task_list(project?, all?)`, `task_message(task, text)`, `task_wait(task, timeout?)`, `search_history(pattern, task?, project?, page?)` (other tasks' whole conversations: one task paged, or every task of a project or of all, a few hits each), `cron_list()`, `cron_add(expr, title, prompt, tz?, overlap?, profile?, skills?)`, `cron_remove(id)`.

**Asking (`ask`)**: `ask(question, options?)`: the task waits for the answer (a notification goes out).

**Secrets (`secrets`)**: `secrets_list()` (names, and whose), `secrets_get(name)` (the value), `secrets_set(name, value)` and `secrets_remove(name)` (the task's project's own secrets only; every project's are the person's; the person hears each change, never the value). The starter rules allow reading (`secrets.secrets_{list,get}`); setting and removing go by the project's default (a migration narrowed the earlier `secrets.*` rule the same way). The person keeps secrets (tokens, keys) for every project and per project (a project's own win over every project's of the same name) in the web UI (settings: every project's; a project's **secrets** tab), the API (`/api/secrets`, values included: the person sees all) and `reagent secret set|list|get|remove [--project]`. They're encrypted in `reagent.db` (XChaCha20-Poly1305) with `secret.key` next to it (made once, the owner's only); a backup of the database alone doesn't give them away. A task's commands and terminals (and the person's terminals for it) get them as environment variables; the context names them; values in any other tool result are replaced by `***` (the `mask` hook, post_tool), and so are they in job-end messages and job logs served by the API (the log on disk keeps them).

**Services (`services`)**: `service_list()` (each one's state, since when, failures, last error, job), `service_add(name, script, health?, interval?, ready_timeout?, stop_timeout?, worktree?, devshell?, description?, notes?)` (adds or replaces; it starts once its command is trusted), `service_remove(name)`, `service_start(name)`, `service_stop(name)`, `service_restart(name)`, `service_logs(name, lines?)` (the end of its output), `service_move(name, to)` (`repo` or `db`). See Services.

**reagent's source (`source`)**: `reagent_source_ls(path?, recursive?)` (a folder's entries, files with their sizes) and `reagent_source_read(path, from?, to?)` (numbered lines, 400 at a time): the repository as this build had it (the crates, the web UI's source and tests, deploy, prompts, the docs and manifests; no build output), built into the binary (rust-embed, `crates/tools/src/source.rs`; a debug build reads the folder). So a task (or an agent outside, through the MCP API) can see how reagent itself works. Allowed by the starter rules and, for existing projects, a migration.

**Todos (`todo`)**: `todo_list()`, `todo_add(items)`, `todo_update(id, status?, text?)` (`pending`, `in_progress`, `done`, `cancelled`), `todo_clear()`: the task's own plan, kept in `reagent.db` (`todos`), so restarts and summaries don't lose it. The context hook shows the list again whenever it changed; the task view shows it live, and the API and the MCP API's `task_get` give it.

**Working memory (`wm`)**: `wm_get()` (every slot as one JSON object, key: value), `wm_set(key, value)` (any JSON; replaces the slot), `wm_remove(key)`: the task's own slots, kept in `reagent.db` (`working_memory`), so restarts and summaries don't lose them. Not injected: the system prompt tells the task to read it now and then, and always after a summary. The task view shows it on its own tab (live: each change is an event, `wm`), and the API and the MCP API's `task_get` give it (`working_memory`). Every project allows `wm.*` (a starter rule; migration 0015 adds it to existing projects); a design task may use it.

**Added servers.** The person adds MCP servers every task gets, or one project's tasks only, on the web UI's **mcp** page (every task's, and each project's; a project's also on its **mcp** tab) or with `reagent mcp add <name> (--url <url> [--header-env VAR --header H --prefix P] | -- <command…> [--env K=V]) [--eager] [--idempotent a,b] [--description …] [--disabled] [--project <id>]` (`mcp list`, `mcp remove`). They're kept in `reagent.db` (`mcp_servers`); a header's value or an env value can come from reagent's environment (`$VAR`, the `.env`), so no secret is stored. Their tools are `<name>.<tool>`, **lazy** by default (subnet's lazy tools: a task sees their names in `load_tools` and loads what it needs; a first call of an unloaded one loads it and asks to call again), or offered from the start (`lazy = false`, `--eager`). Applying (at start, when the web API changes one, and within seconds of a change the CLI wrote) declares them in the cluster, waits until the node runs each or reports why not, then puts the running ones into the mixtures: every task's into `task-<profile>`; a project with running servers of its own gets `task-<profile>--<project>` (the shared ones and its own), which its tasks start from. Names are unique across projects; a project's servers go with it. a server that doesn't start is reported (the settings page shows each one's state) and never blocks tasks. Task agents whose servers changed move onto the new version; new servers reach tasks started after. Names of reagent's own servers are taken. The policy judges their calls like any other.

## Policy

Per project, an ordered list of rules: `tool` (a glob over `<server>.<tool>`), `command` (a glob over the command line, for `shell.exec*`, `shell.job_input`, `pty.pty_open`, `pty.pty_send`), `target` (a glob over what a call is aimed at: the project of `task_spawn`, the path of a file tool), `action` (`allow`, `ask`, `deny`). The first rule that fits decides; none: the project's default. A command line is judged piece by piece (split at `&&`, `||`, `;`, `|`, `&`, newlines; `$(…)` and backticks are commands too; redirections like `2>&1` aren't): the strictest piece wins, so a rule for `cargo *` doesn't allow `cargo test && rm -rf ~`.

It runs as subnet's `pre_tool` hook (`policy`): ask parks the call in subnet's approval state; the person allows it once, always (a rule in front), or denies it; a deny says which rule. subnet's own tools (`search_history`, `grep_result`) are always allowed.

Starter rules: the file, memory, skills and ask tools; reading tools of git, jobs and terminals; subtasks, in the project or another (the subtask then goes by its own project's rules); `ls`, `cat`, `git status/diff/log/add/commit`, `rg`, `grep`, `cargo`, `npm test`, `npm run` are allowed; `git push` and `sudo` ask; `rm -rf /*` is denied. The rest asks.

## Memory

Two scopes, global and each project; each a folder of markdown with an `INDEX.md` the tools keep (one line per file, `- [name](path) — about`, in sections Topics, Folders, Tasks, Other by the path's first folder):

```
INDEX.md
topics/<name>.md          build.md, conventions.md, decisions.md …
folders/<path>.md         notes about a folder of the project
tasks/<id>.md             a task's checkpoints
```

| tool | |
|---|---|
| `memory_read(scope, file?)` | the index, or a file |
| `memory_write(scope, file, text, about)` | makes or replaces a file, with its index line |
| `memory_edit(scope, file, about?, …)` | part of a file (as `fs.edit`) |
| `memory_search(pattern, scope?)` | regex over both scopes' files |
| `memory_remove(scope, file)` | |

`scope` is `global` or `project`; paths are relative markdown paths (`INDEX.md` itself is the tools'). The `context` hook (pre_model) injects the global and the project index, the `AGENTS.md` files (global, the project's from the working directory or else the project folder, and each subfolder's over a path the task touched, shallowest first: the nearer wins where they differ), the rules that apply, the task's todo list and the skills list when the task hasn't seen them as they are now (what changed is shown again). The UI has an editor for both memories.

## Skills

A skill is a folder with a `SKILL.md` (YAML frontmatter `name`, `description`, then the instructions) and files it refers to. **System skills** come first: reagent's own documentation (`reagent`, `reagent-tasks`, `reagent-subtasks`, `reagent-prompt-design`, `reagent-worktrees`, `reagent-policy`, `reagent-secrets`, `reagent-memory`, `reagent-skills`, `reagent-cron-and-triggers`, `reagent-services`, `reagent-tools`, `reagent-interfaces`), written for people and agents alike, kept in `crates/tools/system-skills/`, embedded in the binary and written to `<data>/system-skills/` at every start (so they're read like any skill and always match the running version); their names are taken. The context names them in one line; the web UI's **docs** page shows them (`/api/docs`, `/api/docs/{name}`), and the MCP API has `docs_list` and `docs_read`. Other skills are found (the nearer winning on a name) in the task's working directory (`.agents/skills/`, `.agent/skills/`, `.claude/skills/`, `.codex/skills/`), then the project folder, then globally (`~/.agents/skills/`, Claude Code's `~/.claude/skills/`, Codex's `$CODEX_HOME/skills/` or `~/.codex/skills/`, `<data>/skills/`); read when needed, never copied. The context lists them (`name — description`); `skill_load` gives the body and the skill's files; a task or a cron entry can start with skills loaded into its first message. The project's page lists them with where they're from.

**Rules** are standing instructions (conventions, style, don'ts), not procedures: markdown files in `.agents/rules/` (or `.agent/rules/`), `*.md` or Cursor's `*.mdc`, subfolders too (the name is the path without the extension), in the task's working directory and the project folder, then the global rules folders (`~/.agents/rules/`, `<data>/rules/`), then plugins' (the nearer winning on a name). The project's **skills** tab lists them, with when each applies (`GET /api/projects/{slug}/agent-rules`). Optional frontmatter: `alwaysApply: true`, or neither `globs` nor `description`: always injected; `globs` (a list, or one string split on commas; Claude Code's `paths` too; matched against paths relative to the working directory or the project): injected once the task's file tools touched a matching path (the policy hook notes each `fs.*` call's `path`; kept in memory, so after a restart a rule comes back with the next touch); only a `description`: listed with its path, for the task to read. Each rule is its own part of the context, so it's shown once and again only when it changes.

**Plugins** are git repositories whose skills and rules every task gets, after the global ones (a skill's source is `plugin:<id>`): cloned (shallow) into `<data>/plugins/<id>/` (the id: the URL's last part without `.git`, unless given; letters, digits, `._-`). Their skills are in `skills/`, `skill/` or the generic places under the root (`.agents/skills/`, `.claude/skills/`, …); their rules in `rules/` or `.agents/rules/`. The folder is the record (no table, so the CLI and a running reagent agree at once): the remote, the ref it follows (`git config reagent.ref`; none: the remote's default branch) and the commit. **Updating** fetches that ref (shallow) and resets the folder to it, dropping changes made there; it reports the commits before and after. Made and updated by the person (the settings page; `/api/plugins`: GET, POST `{url, id?, ref?}`, POST `/update` (all), POST `/{id}/update`, DELETE `/{id}`; `reagent plugin add <url> [--id] [--ref]|list|update [ids…]|remove <id>`) and by outside agents (the MCP API's `plugin_list|plugin_add|plugin_update|plugin_remove`). One change at a time in the server (a lock); git runs with no terminal prompt, a URL never taken as an option.

**Prompt templates** are prompts to start tasks from: markdown with YAML frontmatter, the body the prompt with `{{field}}` placeholders (the trigger templates' rendering). Frontmatter: `description`, `title` (placeholders too; none: the task names itself), `skills`, `budget`, `profile`, `kind`, `project` (a global one pinned to a project: picking it means that project; elsewhere it's refused), `worktree` (a persistent worktree the task starts in), `fields` (`name`, `label`, `type`: `text` (default), `multiline`, `select` (with `options`), `checkbox` (renders yes or no); `default`, `required`); any other key, a field without a known type, a select without options or an empty body makes it **broken** (listed with why, never used). With fields a template is **form-like**: the values are checked (required, a select's options, no unknown field), defaults filled, and the prompt and title rendered by reagent. Without, it's **plain**: its body is a prompt to edit. Starting from one (`StartTask.template` and `values`: the web API's `POST /api/tasks`, the MCP API's `task_start`, `tasks.task_spawn`, `reagent task start --template <name> --set field=value`), what isn't asked for comes from it: the prompt, the title, the skills, each limit (then the project's), the profile, the kind, the project, the persistent worktree. Found (the first winning on a name): the project's `.agents/templates/` (or `.agent/templates/`; subfolders too, the name its path without `.md`), those **kept in reagent** (`templates` in reagent.db: the whole file, a project's or every project's; made on the project's templates tab or in the settings, `PUT /api/templates` `{id?, project?, name, text}` (a broken one is refused), `DELETE /api/templates/{id}`), the global folders (`~/.agents/templates/`, `<data>/templates/`), then plugins' (`templates/`, `.agents/templates/`). Listed by `GET /api/templates?project=` (parsed, with source, path, error), the MCP API's and tasks' `template_list` (no paths or file text: a form's fields, or a plain one's prompt), and `reagent template list [--project] | show <name>`. `tasks.template_list` is allowed by the starter rules and, for existing projects, a migration.

## The designer

A guide more than a prompt writer: from a rough goal it works out with the person what they actually want done and the best way for reagent to do it, and proposes the work (`crates/tools/src/design.rs`; what it knows about clear prompts and which item fits is the system skill `reagent-prompt-design`, loaded into it, so people and agents read the same).

It runs as a **design task** (origin `design`, title `Design: <goal>`, `design_profile` from reagent.hcl, else the usual profile): it may only read and ask (the policy hook refuses every other tool for it: the file tools that read, memory reading, skills, `ask.ask`, `search_history`, the task, cron and trigger lists, todos). It reads the project first, asks the person what changes the result and the project doesn't show (one question a call, each with likely answers; about ten at most), points out risks and checks, and ends with a note and a **proposal**: a ```json block (the last in its report) `{note, items}`, with items of any kind and number: `task` (title, prompt, skills, kind, profile, budget), `cron` (expression, time zone, title, prompt, skills), `trigger` (name, mode, schedule, script, templates, secret; in the repo unless said), `skill` (a repo skill: name, description, the SKILL.md body), each with a `why`. A target says what the person started from (`task`, `cron`: a prompt that runs again and again; `trigger`: templates with `{{key}}`, `{{vars.x}}`; `subtask`). Items that aren't one are dropped, and so is what they name that doesn't exist (a skill, a kind, a profile). Reading it is lenient where models are: the JSON is read to its own end (a skill's body may hold ``` fences), a ```json inside a string is passed over, and a bare list of items or a single item (its `note` in it) is taken too, an item without `type` typed by its fields (`expr`: cron; `mode`/`script`: trigger; `body`: skill; else task). The task page shows the report without the block, next to the proposal (each item editable, a task switchable to a cron entry and back); a finished design task whose report has none readable says so, with a button that messages it to write the proposal again.

The person edits the items, ticks the ones they want, and creates them: a task starts (or queues), a cron entry and a trigger are made (a repo trigger's files written), a skill is written to `.agents/skills/<name>/SKILL.md` (never over an existing one). Files go into the project folder for the person to commit.

- **Web UI**: "design it with the guide" in the new-task, cron and trigger forms starts a design task and opens it. While it asks, its page has "you decide" and "propose now" besides the options; when it's done, the proposal: the note, each item (markdown, editable, a checkbox; a task also "open in the form"), "create the ticked ones" and what became of each.
- **API**: `POST /api/design` (`{project, goal, target?}` → the task), `GET /api/tasks/{id}/proposal` (null until it has one), `POST /api/design/create` (`{project, items}` → what became of each).
- **Agents**: `tasks.prompt_design(goal, project?)` starts a design task as the caller's subtask (allowed by the starter rules, and by a migration for existing projects); the person answers its questions, and its report (the proposal) comes to the caller as a message.
- **MCP API**: `prompt_design` (the design task's id; `task_wait` and `task_answer` follow it), `design_proposal`, `design_create`.
- **CLI**: `reagent task design --project <id> [--target …] "<goal>"` adds the design task queued (the running reagent starts it); `reagent task proposal <id> [--make all|1,3] [--json]` shows its items and makes those (tasks queued).

## Cron

Per project: a five-field expression and a time zone (`croner`, `chrono-tz`), a task title and prompt, options (profile, budget, skills), what happens while the last run still goes (`skip`, default; `queue`: it starts when the last ends; `parallel`), and `catch_up` (a run missed while reagent was down runs once; without it, it's skipped). Checked every 15 s. Managed in the UI (next and last runs, run now, on/off) and by tasks. A run that can't start is a notification.

## Triggers

A trigger runs a script that watches something (a CI pipeline, a queue, an inbox) and turns what it sees into events; an event starts a task or goes to a running one as a message. Per project (`crates/tools/src/triggers.rs`), three modes:

- **poll**: runs every `every` seconds (at least 10; `90s`, `2m`, `1h` where a duration is written) or on a cron expression (with `tz`; its first run is at its first time, an `every` poll's at once); killed (its process group) after `timeout` (default 60 s). Run by reagent itself, stdout read for events, stdout and stderr kept as the run's output.
- **watch**: runs for good as a supervisor job (owner `trigger:<project>/<name>`; it outlives restarts like any job), its complete output lines read every second from where it was (a byte offset kept in its state); when it ends, it's counted like a run and started again after `every` (default 5 s), or later when it failed.
- **webhook**: `POST /hook/<project>/<name>`, outside the login, checked against a secret the trigger names (one of the project's secrets): GitHub's `X-Hub-Signature-256` (HMAC-SHA256), GitLab's `X-Gitlab-Token`, or `Authorization: Bearer` (no secret, a missing one, or a bad signature: refused). Answered `202` at once. With a script, `{headers, body}` (minus the credential headers) goes to its stdin and it prints the events (to filter: only failed pipelines); without one, the body is one event (key: `X-GitHub-Delivery`, `X-Gitlab-Event-UUID` or `X-Request-Id`, else the body's hash; vars: the body).

**Events.** A script prints one JSON object per line on stdout: `{"key": "pipeline-812", "to": "new", "title": "…", "message": "…", "vars": {…}}`; other lines are its log, a line starting with `{` that isn't an event is an error. Exit 0 with no events is "nothing happened"; any other exit is a failure. `to` is the script's choice: `new` (the default) starts a task from the trigger's title and prompt templates (`{{key}}`, `{{title}}`, `{{message}}`, `{{vars.a.b}}`, `{{vars.list.0}}`; text as it is, anything else as JSON, missing as nothing; an event's `message` the prompt doesn't use is appended, its `title` replaces the trigger's); `running` sends `[trigger <name>] <message>` to the newest active task this trigger started (or starts one if none is); a task id (of the same project) sends it to that task. A key seen before (by this trigger, within 30 days; none given: the line's hash) is dropped. For anything more (cursors, last-seen ids) the script keeps its own state in `$REAGENT_STATE` (`<data>/triggers/<project>/<name>/`, kept). New tasks follow the trigger's `overlap` (`skip`, default; `queue`: the event waits in its state and starts when the trigger's last task ends; `parallel`) and options (profile, kind, skills, budget); their origin is `trigger:<project>/<name>`.

**Running.** Like a task's commands: in the project folder, in its dev shell (by the project's setting; `devshell = false` per trigger), with the project's environment and secrets, plus `REAGENT_TRIGGER`, `REAGENT_STATE`, `REAGENT_LAST_RUN` (unix seconds) and `REAGENT_TASKS` (JSON: the trigger's active tasks with their keys, so it can choose `to`). A kept trigger's script is written to its state folder (`script`) and run with `sh` (or itself, with a `#!` line); a repo trigger's runs from the repo. Each run (its output's end, masked; the events it dispatched and what became of them; its error) is kept in `trigger_runs`, the last 20 (the triggers tab shows them).

**Made by** the person (the project's **triggers** tab, `PUT /api/triggers/<project>/<name>`, `reagent trigger add|list|run|enable|disable|move|approve|remove --project <id>`), by tasks (`triggers.trigger_add|trigger_list|trigger_remove|trigger_move`; made by `task:<id>`), by outside agents (the MCP API's `trigger_list|trigger_add|trigger_remove|trigger_run|trigger_move`; made by `mcp`), and by the repo: `.agents/triggers/<name>/TRIGGER.md` (or `.agent/triggers/`) in the project folder, like a skill: YAML frontmatter (`description`, `mode`, `every`|`cron`, `tz`, `script` (a file beside it, default `run`), `timeout`, `overlap`, `title`, `profile`, `kind`, `skills`, `budget`, `secret`, `devshell`; anything else is an error) and the prompt template as the body. Repo triggers are read every 10 s into `reagent.db` (their copy, with what reagent keeps: on/off, state); one that can't be read is shown on the tab; one whose files are gone goes; a kept trigger of the same name wins (and the clash is shown). Editing a repo trigger in the UI writes its files. A task's triggers are like anyone's: they outlive it. A trigger moves into the repo and back (the tab's "move to repo" / "move to reagent", `reagent trigger move <name> repo|db`, `trigger_move`): into the repo writes `.agents/triggers/<name>/TRIGGER.md` and its script into the project folder (left for the person to commit); back keeps it in `reagent.db` and deletes the files. Names are unique within a project wherever a trigger lives, and its id (`<project>/<name>`), seen keys, runs, state, failure streak and approval go with it. Removing a repo trigger removes its files.

**Trust.** Whether a script runs: the person allowed this script (by its hash: what they save in the UI or CLI is allowed; an approval or a denial holds until the script changes), else the project's policy, judged as the call `triggers.run` with the command `./.agents/triggers/<name>/<file>` for a repo trigger or the script's text for a kept one (piece by piece, like a shell command): `allow triggers.run cmd "./.agents/triggers/*"` trusts the repo's. An "ask" is a `trigger` notification (once per script) and waits in the inbox and on the tab: allow this script, always allow (a rule for that command goes in front), deny. A denied script doesn't run (said once).

**Failures.** A failing run (exit, crash, timeout, a bad event line, an event that couldn't be delivered) backs off (`every` (or 60 s) doubled per failure in a row, up to an hour) and shows as failing with its last error. After 5 in a row a task is started (origin `trigger-repair:<project>/<name>`, once per streak; queued until nothing else goes on in the project, see Tasks at once) with the trigger, its script, where it's kept and the last error and output, to repair it, and the person hears it (a `trigger` notification); a run that works again (or a change saved) ends the streak.

**Example: a failed CI run.** A poll every 2 minutes: `gh run list --branch main --status failure --json databaseId,url,displayTitle -L 5 | jq -c '.[] | {key: (.databaseId|tostring), vars: .}'`, prompt "CI run {{vars.url}} failed ({{vars.displayTitle}}). Find out why and fix it in a worktree." The first sighting of each failed run starts one task.

## Services

A service is a command of a project that should always run: a dev server, a database, a queue worker, a tunnel. reagent starts it, checks it, restarts it when it ends or stops answering, and when restarting doesn't help, starts a task to repair it, like a failing trigger (`crates/tools/src/services.rs`).

**Defined** like triggers: kept in reagent.db (`services`), or in the repo as `.agents/services/<name>/SERVICE.md` (or `.agent/services/`), read every 10 s, moved either way (`move`). Frontmatter: `description`, `script` (a file beside it, default `run`; a kept one's script is its text), `health` (a command: exit 0 is healthy), `interval` (between checks while it's up, default `30s`), `ready_timeout` (how long it may take to come up, default `60s`), `stop_timeout` (SIGTERM, then SIGKILL after it, default `10s`), `worktree` (a persistent worktree of the project to run in; default the project folder), `devshell` (default true); anything else is an error. The body is notes for whoever repairs it (what it is, where its config lives, how it's usually fixed); it goes into the repair task's prompt. Names: lowercase letters, digits, `-`.

**Running.** As a supervisor job (owner `service:<project>/<name>`; it outlives restarts of `reagent up`, which picks it up again from its state), in its folder, through the project's dev shell (unless `devshell: false`), with the project's environment and secrets plus `REAGENT_SERVICE`. The health command runs the same way (killed after 10 s). A loop every second looks after each one:

- **starting**: started and not yet up. With a `health` command it's checked every 2 s and is **up** once a check passes; without one, it's up once it has lived 3 s. Not up within `ready_timeout`: stopped, and that's a failure.
- **up**: checked every `interval`; 3 failed checks in a row: **unhealthy**, stopped, a failure. Up for 60 s ends a failure streak.
- An end (any exit, a signal, lost with the supervisor) is a failure: it's started again after a backoff of 5 s doubled per failure in a row, up to an hour (**backoff**). After 5 failures in a row a task is started (origin `service-repair:<project>/<name>`, once per streak; queued until nothing else goes on in the project, see Tasks at once) with the service's definition, notes, where it's kept, its last error and the end of its output, to repair it, and the person hears it (a `service` notification).
- **stopped**: switched off (`enabled = false`): a stop (the person's, a task's, an outside agent's) holds until a start. Stopping sends SIGTERM to its process group, SIGKILL after `stop_timeout`. A start clears the streak and starts it at once; a restart stops it and starts it again; a changed definition restarts a running one.

Each start is recorded in `service_runs` (the last 20: started, up, ended, exit, error, the end of its output). Its output is the job's log (`/api/jobs/{id}/output`, masked like any job's).

**Trust** as for triggers: the person's own saves are allowed (by the hash of its script and health command); otherwise the project's policy decides the call `services.run` with the command `./.agents/services/<name>/<file>` for a repo service or the script's text for a kept one (and the health command, judged the same way): allow, deny (not started, said once), or ask: a `service` notification and a wait in the inbox and on the tab (allow this one, always (a rule in front), deny).

**Managed by** the person (the project's **services** tab, the API, `reagent service …`), tasks (`services.service_list|service_add|service_remove|service_start|service_stop|service_restart|service_logs|service_move`; list and logs are allowed by the starter rules and, for existing projects, a migration; made by `task:<id>`), and outside agents (the MCP API's `service_*`, made by `mcp`).

## Web interface

Vue + Parcel (`webui/`), built into `webui/dist` and embedded in the binary (rust-embed; a debug build reads the folder): served by `reagent up` (hashed assets cached for good, the page and the service worker not); live over SSE (`/api/events`).

- **Every page:** ↑ and ↓ jump to the top and the bottom; ↓ then follows the bottom as the page grows (a live transcript, a job's output) until the person scrolls (wheel, touch, scroll keys, the scrollbar) or presses ↑.
- **Docs:** the system skills, rendered.
- **Inbox:** waiting tasks (approvals, questions, merges, budgets), triggers whose script waits for approval (allow, always, deny), failed ones, tasks going on, new notifications (each one line, unfolding to its body; marked seen one by one or all at once: `POST /api/notifications/seen` with `{id}` or `{upto}`).
- **Quick prompt** (`#/quick`): a task for any project fast: the project, a template (a form-like one shows its fields and the prompt rendered live; a plain one fills the prompt to edit; one pinned to another project moves there; either sets the title, skills, limits it gives), where it works (the project folder or a persistent worktree), an optional title, what to do, each limit (tokens, cost, minutes) from "project default" (showing it), presets, "unlimited" or typed, skills by search; the project and limits are remembered in the browser for the next one.
- **Projects:** the list and adding one; a project's tabs: tasks (a tree, subtasks under their parent), templates (the project's, kept, global and plugins', broken ones with why; kept ones made, edited, removed), new task (a template, as on the quick prompt; where it works; title, optional; profile, budget, skills picked by searching their names and descriptions), cron (run now, edit, on/off), triggers (each with its schedule, where it's kept, its approval, failures and last runs; run now, edit, on/off, move to the repo or back, remove; a webhook's URL), services (each one's state, since when, failures and last error, its output; start, stop, restart, edit, move to the repo or back, allow or deny its command; its last starts), worktrees (the persistent ones: make, adopt one git knows, sharing, status and diff, merge into the base, remove; the tasks that worked in each), policy (the rules, ordered), memory, skills, mcp (its own servers), settings.
- **Task:** state, usage and cost; its todo list (live); pause, pause after this turn, resume, start now (a queued one), retry, clone and restart (a task that's over: a new one from the same prompt, profile, kind, skills and budget), cancel, open a terminal; what it waits for, pinned on top while you scroll and foldable to one line (approve once / always / deny with the call's arguments; answer with an option or text; merge with the diff, or send back; raise the budget); its reports (every one, oldest first, each foldable and the whole section too; the earlier ones start folded); a design task's proposal; a message box (and the messages queued but not taken yet, oldest first: each editable and cancellable until it's being delivered, or all cancelled at once); subtasks; tabs: the transcript (the whole conversation, summarised parts folded, the answer streaming; the person's and the model's text, summaries and the report rendered as markdown (`markdown-it`, raw HTML off), tool calls and results as they are), jobs (a click opens a job's log in a modal: the last 1000 lines, earlier ones on demand, live while it runs; to background, stop, kill), terminals (xterm.js over a WebSocket), the worktree's diff, the working memory (each slot, live).
- **Search:** every task's conversation.
- **MCP:** added servers, every task's and each project's (URL or command, header from env, env, lazy or eager, idempotent tools, on/off; whether each runs).
- **Settings:** push on this browser, prompt templates kept for every project, the notification channels, the plugins (add from a git URL with an id and a branch or tag; each one's URL, commit, skills and rules; update one or all; remove), the profiles, API tokens (make: shown once; revoke), the global memory.

Login: one password (`reagent passwd`, argon2), a session cookie (`HttpOnly`, `SameSite=Strict`, `Secure` behind TLS, 30 days, kept hashed), five tries a minute per address, writes only from the same site (Origin). The API, all behind the login: `/api/session`, `login`, `logout`, `config`, `settings`, `design` (+ `/create`), `tasks/{id}/proposal`, `docs` (+ `/{name}`), `events`, `inbox`, `notifications`, `push/*`, `projects` (+ `/{id}`, `/rules`, `/skills`, `/cron`, `/worktrees`: the persistent ones and the adoptable, post to make or adopt one; `/worktrees/{name}`: get (status, diff, tasks), put (sharing), delete (`?force`, `?delete`), `/merge`; `/services`), `services/{project}/{name}` (put, delete; `/start`, `/stop`, `/restart`, `/approve`, `/move`, `/runs`), `memory`, `cron`, `triggers/{project}/{name}` (put, delete; `/run`, `/enabled`, `/move`, `/approve`, `/runs`; a project's list at `projects/{id}/triggers`), `mcp` (`?project=<id>|global`; `/{name}`: put, with `project`, applies at once), `tasks` (+ `/{id}` and `/transcript`, `/message`, `/pause`, `/resume`, `/cancel`, `/retry`, `/start`, `/limits`, `/raise`, `/profile`, `/approve`, `/answer`, `/merge`, `/diff`, `/jobs`, `/ptys`), `search`, `jobs/{id}/output|stream|background|kill`, `ptys/{id}` (WebSocket), `tokens`.

## MCP API

Agents outside use reagent at `/mcp` (streamable HTTP) with `Authorization: Bearer <token>`. Tokens are made with `reagent token add <name>` or in the settings (shown once, kept hashed, revocable). Tools: `projects`, `task_start`, `task_list`, `task_get` (state, what it waits for, report, every report, subtasks), `task_transcript`, `task_message`, `task_pause`, `task_resume`, `task_cancel`, `task_retry`, `task_raise_budget`, `task_switch_profile`, `task_approve`, `task_answer`, `task_merge`, `task_wait` (until it ends or waits for someone), `search`, `prompt_design`, `design_proposal`, `design_create`, `docs_list`, `docs_read`, `trigger_list`, `trigger_add`, `trigger_remove`, `trigger_run`, `trigger_move`, `plugin_list`, `plugin_add`, `plugin_update`, `plugin_remove`, `template_list`, `worktree_list`, `worktree_add`, `worktree_merge`, `worktree_remove`, `service_list`, `service_add`, `service_remove`, `service_start`, `service_stop`, `service_restart`, `service_logs`, `service_move`, `reagent_source_ls`, `reagent_source_read`; `task_start` takes `worktree` (a persistent one), `template` and `values` too (its project may be left out for a template pinned to one).

## Notifications

Events: `done`, `failed`, `waiting` (an approval, a question, a merge), `budget`, `cron` (a run that couldn't start), `model` (a task moved onto another profile), `trigger` (a script waiting for approval, denied, or failing into a repair), `service` (a command waiting for approval, denied, or failing into a repair), `secret` (a task set or removed one of its project's secrets). Bodies are markdown. Every one is kept (the inbox shows them, rendered) and sent: by Web Push and to reagent.hcl's apprise URLs as `notify.events` asks (default all), to each apprise channel as its own list asks (default all):

- **Web Push:** VAPID keys made once (in the settings table), a browser subscribes from the settings page (a service worker); sent encrypted with `web-push-native` (pure Rust); its body as plain text (the system doesn't render markdown); a click opens the task. Gone subscriptions are forgotten. A notification that waits for the person has **buttons**: an approval "Allow once" and "Deny", a question its first two options, a merge "Merge". Each is a one-time token (32 random bytes, kept hashed in `action_tokens`, good for a day); the service worker posts it to `/api/action` (no login: the token is the authority), which does it only if the task still waits for exactly that (the same call, question or branch), and shows a notification saying whether it was done.
- **apprise:** `apprise -v -i markdown -t <title> -b <body and a link> <urls…>` (each service gets the format it takes; `-v` so a failure says why, naming the service, not the URL); it's a Python CLI, run, not linked. A failed send is tried once more after 2 s (a first connection now and then fails). The URLs: the person's **channels** (`notify_channels` in reagent.db: a unique name, the URL encrypted like secrets with `secret.key`, the kinds it gets or all, on or off), added on the settings page or with `/api/notify/channels` (GET lists them with the URL masked to its scheme and last six characters, and how many URLs reagent.hcl has; POST `{name, url, events?}`; PUT `/{id}` `{enabled}`; DELETE `/{id}`; POST `/{id}/test` sends a test and returns what apprise said), and, optionally, reagent.hcl's `notify.apprise` and `notify.apprise_env`.

```hcl
  provider = "deepseek"
  model    = "deepseek-chat"
  price    = { input = 0.27, cached = 0.07, output = 1.10 }   # per million tokens, for budgets; cached: input served from the provider's cache (none: the input price)
  context  = 1000000                           # compaction at three quarters
  # params = { temperature = 0.2 }
  # grep_results = { over = 8000 }             # this profile's own cut-off

# Long tool results reach a task cut, with a note; grep_result reads the rest. 0: off.
grep_results = { over = 12000, except = ["skills.skill_load", "fs.read", "shell.job_output"] }
search_history = true

  apprise = ["tgram://…"]                      # optional, besides the channels in reagent.db; and/or apprise_env = "REAGENT_APPRISE"
  events  = ["done", "failed", "waiting", "budget", "cron"]
  url     = "https://reagent.example.org"      # links in notifications
}
```

## Building

`cargo build --release -p reagent --target $REAGENT_MUSL_TARGET` in the dev shell gives one static (musl, static-pie) binary with the web UI in it (build `webui` first); the dev shell carries the musl target and a static C toolchain for SQLite and the TLS crypto. subnet is used without its default features (no tool router: fastembed's ONNX runtime has no static musl build; no hub web UI). `deploy/push.sh` copies just that binary.
